Teaching note

Production-ready AI / Agentic Engineering

AI 能做，不代表可以放心上線。

真正的正式環境，不靠「相信模型」。它靠清楚的規格、能限制損害的邊界，以及可重複驗證的證據。

能力回答「做不做得到」；工程回答「敢不敢交付」。

01 / Gates

正式環境前，先過三道關卡

這三道關卡分別處理不同風險。Spec 避免 AI 猜錯方向，安全邊界限制錯誤的破壞範圍，Evaluation 則確認成果是否真的值得發布。

01

把話講清楚

把意圖、背景、工具、禁區與完成標準寫進可審查的 Spec。

Output · Direction
02

把邊界設好

預設 Agent 可能犯錯，用隔離、權限與人工 checkpoint 限制後果。

Output · Containment
03

把驗收做好

留下可觀測證據，依客觀標準判斷功能、品質與風險是否可接受。

Output · Evidence
02 / Specify

Spec 的任務，是讓 AI 沒有必要猜

好的 Spec 不必很長，但至少要回答五個問題。它也是團隊與 AI 共用的意圖來源，需求改變時先改 Spec，再改實作。

01

做什麼

要解決的需求與可交付成果。

02

為什麼做

使用者、情境與真正目的。

03

用什麼做

允許的工具、框架、版本與來源。

04

什麼不能碰

資料、環境、權限與明確禁區。

05

什麼叫做完

可觀察、可重複的驗收標準。

用 Given / When / Then 寫完成標準

Given已知情境使用者已登入，並停留在個人設定頁。
When執行動作更新顯示名稱並按下儲存。
Then可見結果成功訊息出現，重新整理後仍保留新名稱。

別漏掉失敗情境：輸入不合法時應顯示明確提示，而且不應寫入資料。

03 / Contain

安全設計不是要求 AI 永遠不犯錯

比較可靠的思路，是先假設錯誤一定會發生，再讓錯誤停在可承受的範圍內。高風險動作不能只靠提示詞提醒。

01

隔離執行

讓不受信任的程式在可丟棄的 sandbox 或測試環境中執行，不能直接碰正式資料與主機。

Evidence · 隔離範圍
02

風險式簽核

部署、資料庫變更、付費與不可逆操作必須停下來。簽核前先提供人看得懂的意圖與變更摘要。

Evidence · Diff + Plan
03

供應鏈控管

依賴套件只從可信來源取得，鎖定版本，確認名稱與維護狀態，並在 CI 中執行安全掃描。

Evidence · Lockfile + Scan
04 / Distinguish

沒有越界，不等於做得正確

Security 與 Evaluation 是兩條不同的判斷線。只做其中一條，都不足以決定成果是否能進正式環境。

Security

Agent 有沒有做不該做的事？

  • 是否碰到未授權資料或環境
  • 是否執行不可逆或高風險動作
  • 是否引入可疑依賴或洩漏敏感資訊
通過代表：錯誤被限制在邊界內。

Evaluation

Agent 做出來的東西值不值得交付？

  • 功能是否符合原始意圖與驗收條件
  • 使用者實際看到的結果是否正確
  • 品質是否穩定，而且能重複驗證
通過代表：成果有足夠證據可以發布。
05 / Evaluate

先看得見，才有辦法驗收

可觀測性把對話、工具呼叫、狀態與結果留成證據。驗收則用這些證據判斷 Agent 是否偏題、是否收斂，以及錯誤是否反覆出現。

Observable evidence

只看最後一句回答，無法判斷 Agent 中間做了什麼。至少要能回看：

  • 01原始目標與使用的 Spec 版本
  • 02工具呼叫、參數、結果與錯誤
  • 03變更內容、測試證據與人工簽核
  • 04時間、成本與重試次數
01

保存原始任務

每個步驟都回頭對照最初要求，檢查是否越做越偏。

02

驗成品，不只驗程式

網頁就實際操作桌面與手機；報表就讀結果與數字，而不只看 code。

03

看是否收斂

記錄修改幾輪才達標。反覆修不好的任務，是最值得研究的失敗樣本。

04

保存每次糾正

把「不對、不是這樣」轉成測試案例、規則或新版 Spec，形成可重用的防錯資料。

06 / Review

AI 加速產出後，瓶頸會移到 Review

如果每個小動作都要求人按同意，人很快會失去注意力。更好的分工，是讓自動檢查處理日常證據，把人的判斷留給架構、風險與不可逆決策。

Machine

自動檢查

格式、測試、依賴、漏洞、權限與既定驗收條件。

→
Human

高價值判斷

需求是否合理、架構取捨、風險承受度與是否值得發布。

→
Merge

條件式批准

人的方向批准，加上自動化證據全部通過，才允許進入下一階段。

07 / Apply

下一個功能，就從這張清單開始

不需要一次建立完整平台。先對下一個真實功能補齊三道關卡，再把失敗案例逐步寫回流程。

  • 先寫一份至少回答五個問題的 Spec。
  • 用 Given / When / Then 定義成功與失敗情境。
  • 把正式環境、資料庫與金流列為明確禁區。
  • 讓程式在隔離環境中執行，並限制權限。
  • 高風險動作前提供白話變更摘要與人工 checkpoint。
  • 驗收實際成品，保存每次糾正作為下一輪測試。

開工前提示詞

在開始實作前，先把我的需求整理成 production-ready spec。

請依序確認：
1. 要做什麼，以及為什麼做
2. 允許使用的工具與版本
3. 禁止接觸的資料、環境與操作
4. Given / When / Then 驗收條件
5. 失敗與邊界情境
6. 測試、觀測與人工簽核點

先輸出 spec 與風險清單，等我確認後再實作。
不要部署、修改正式資料或執行不可逆操作。
